# 持续集成与固件发布

工作流入口为 `.github/workflows/build.yml`。板型和发布变体来自
`main/boards/**/config.json`，本地与 CI 均通过 `scripts/build.py` 构建。

## 构建范围

- `main` 上影响固件的提交、手动运行和发布构建验证全部发布变体。
- PR 和开发分支的板级修改只构建受影响的板型；公共代码、SDK 配置及构建脚本修改触发全量构建。
- 文档和测试源码修改不启动固件编译；新分支缺少差异基线时全量构建。
- force-push 后若旧提交不在检出历史中，尝试按 SHA 获取；无法获取时全量构建。
- `workflow_dispatch` 提供手动全量验证入口。后续提交自动取消同分支或同 PR 的旧运行；发布运行保留。

## 编译与缓存

固件使用官方 `espressif/idf:v6.1.1` 容器，并核对
`.github/actions/setup-idf/action.yml` 中固定的 SDK 提交。
同芯片变体按最多八个一组顺序构建，共享 ccache 和组件下载缓存。
每个变体从已拉取 LFS 资源的检出目录复制受版本控制的文件，在干净的源码工作区中构建，
完成后删除工作区。构建目录、CMake 缓存、生成资源、sdkconfig、依赖锁文件和
managed_components 均重新生成，避免板型状态相互影响。源码快照保留 Git 提交信息，
复制实际 LFS 文件内容，不使用包含 LFS 指针的归档。

ccache 按固定的芯片分组恢复，单组限制为 256 MiB；组件下载缓存按芯片和依赖声明区分。
缓存不包含生成的 sdkconfig、managed_components 或整个构建目录。
更换 SDK 会使用新的编译缓存空间，缓存缺失不影响构建正确性。
部分板型失败时仍保存已生成的缓存，缓存服务失败不影响固件构建结果。

各组失败后继续构建剩余变体，任务汇总记录各变体的状态和耗时，并上传日志、
SHA-256 清单及成功的固件 ZIP。产物保留七天。统一的 `CI result` 检查汇总固件构建结果，也适用于没有固件改动的运行。

## 发布

发布标签使用 `xiaoling/v<PROJECT_VER>`，必须与 CMake 中的版本一致。
发布优先复用同一仓库、同一提交上已成功完成的 main 构建，要求所有分组产物仍有效；
同一提交的 main 构建仍在运行时最多等待 140 分钟，避免并行重复编译；
没有可用产物、构建失败或等待超时后完整构建。PR、其它分支、失败运行及过期产物不能作为发布来源。

上传前校验全部变体的板型、芯片、提交号与 ZIP 的 SHA-256，任何缺失或不一致都会阻止上传。
每个发布 ZIP 保持包含 `merged-binary.bin`，文件名为 `xiaoling_<变体>_v<版本>.zip`。
只有发布任务拥有仓库内容写权限。
